1. Why must the key and IV be the same for Encrypt and Decrypt?

Decryption runs every step of encryption in reverse, so it needs exactly the same algorithm, mode, padding, key, and (for CBC) IV. That is what "symmetric" means: one secret, used in both directions.

  • Key: secret, agreed in advance (pre-shared or exchanged with a key-exchange protocol), never sent with the message.
  • IV: not secret. It is sent with the ciphertext, usually as its first block.
  • Algorithm, mode, padding: agreed in advance, like the key, but not secret.

Try it: encrypt, change one value in the middle panel, then decrypt.

  • Different key: every block decrypts to random-looking bytes, and the padding check usually fails.
  • Different IV (CBC): only the first block is wrong; the rest decrypts correctly. A wrong IV can go unnoticed in a long message.
  • Edited ciphertext (CBC): the edited block is garbled and the same bits flip in the next block.
2. Modes of operation: when is an IV needed?

A block cipher only encrypts one block (16 bytes for AES/ARIA, 8 bytes for DES/3DES). The mode decides how longer messages are handled. Only ECB uses no IV.

ModeIV / noncePaddingNotes
ECBNoneNeededEach block encrypted on its own. Equal plaintext blocks give equal ciphertext blocks, so patterns leak. Avoid.
CBCIV, one block, unpredictableNeededEach block is XORed with the previous ciphertext block before encryption.
CFB / OFBIV, one blockNot neededTurn the block cipher into a stream cipher.
CTRNonce/counter, never reused with the same keyNot neededEncrypts a counter and XORs it with the data; parallel.
GCMNonce (usually 12 bytes), never reused with the same keyNot neededCTR plus an authentication tag. Detects tampering. The usual choice today.

3. Is there a standard IV value?

No. Standards define requirements, not a fixed IV for encryption. NIST SP 800-38A Appendix C requires a CBC IV to be unpredictable: generate it with an approved random bit generator for every message, or encrypt a unique nonce with the same key.

  • The default IV here, 00 01 02 … 0f, comes from the NIST SP 800-38A test vectors. It is used only so results can be reproduced.
  • Fixed values do appear in other constructions: CBC-MAC and CMAC start from an all-zero block, and AES Key Wrap (RFC 3394) uses A6A6A6A6A6A6A6A6. These are not general-purpose encryption IVs.
  • Legacy systems sometimes use an all-zero IV or a string such as 0123456789abcdef. That is a private convention, not a standard: the same plaintext always gives the same ciphertext, and a predictable CBC IV enables chosen-plaintext attacks (for example BEAST against TLS 1.0).
4. "I never set an IV": what libraries do by default

There is no default IV value. When code does not set one, the library either creates a random IV, derives one from a password, or uses a mode without an IV.

5. "Encrypted in C# without an IV, decrypted in Java." Why does it work?

With a random IV that is not sent, Java could not decrypt the first block. When it works, one of these is usually true:

  • Both sides use ECB: aes.Mode = CipherMode.ECB or aes.EncryptEcb(...) in C#, and Cipher.getInstance("AES") in Java.
  • The IV is derived from the password: Rfc2898DeriveBytes gives both aes.Key and aes.IV.
  • A helper sets it: often the first 16 bytes of the key, or an all-zero array. This is a fixed IV.
  • The IV is prepended to the ciphertext: Java reads the first 16 bytes as the IV. This is the correct approach.

Quick check: encrypt the same plaintext twice with the same key. Identical results mean ECB or a fixed IV; different results mean a random IV travels with the data.

C# PaddingMode.PKCS7 and Java PKCS5Padding are the same scheme for 8- and 16-byte blocks.

6. Padding and "No padding"

ECB and CBC only work on whole blocks, so the last block is filled with padding.

Padding3 bytes neededNotes
PKCS#703 03 03Default in .NET, OpenSSL, Node.js, and Java (named PKCS5Padding). Adds a full block when already aligned.
ANSI X.92300 00 03Always adds padding.
ISO/IEC 7816-480 00 00Always adds padding.
Zero00 00 00Only when needed. Original trailing zero bytes are lost.
None-The caller must provide whole blocks.

"No padding" does not fill anything automatically. Libraries reject a partial block: .NET "The input data is not a complete block.", Java IllegalBlockSizeException, OpenSSL "data not multiple of block length". Modes such as CTR and GCM need no padding at all.

1. 왜 Encrypt와 Decrypt의 Key와 IV가 같아야 하나요?

복호화(decryption)는 암호화(encryption)의 모든 단계를 거꾸로 수행합니다. 그래서 알고리즘, 운영 모드(mode), padding, 키(key), 그리고 CBC라면 IV까지 정확히 같아야 합니다. 하나의 비밀 값을 양방향에 똑같이 쓰는 것, 이것이 "대칭(symmetric)"의 의미입니다.

  • Key: 비밀 값. 미리 합의하거나(pre-shared) 키 교환 프로토콜(key exchange)로 나눠 가지며, 메시지와 함께 보내지 않습니다.
  • IV: 비밀이 아닙니다. 보통 암호문 맨 앞 블록에 붙여서 함께 보냅니다.
  • 알고리즘, 모드, padding: 키처럼 미리 합의하지만 비밀은 아닙니다.

직접 해 보기: 암호화한 뒤 가운데 패널의 값 하나를 바꾸고 Decrypt를 누르세요.

  • 키가 다르면: 모든 블록이 무작위처럼 보이는 bytes로 풀리고, 대부분 padding 검사에서 실패합니다.
  • IV가 다르면(CBC): 첫 블록만 틀리고 나머지는 정상적으로 풀립니다. 긴 메시지에서는 잘못된 IV를 알아채지 못할 수도 있습니다.
  • 암호문을 수정하면(CBC): 수정한 블록은 깨지고, 다음 블록의 같은 위치 bit가 뒤집힙니다.
2. 운영 모드(mode of operation): IV는 언제 필요한가요?

블록 암호(block cipher)는 한 번에 한 블록만 암호화합니다(AES/ARIA 16 bytes, DES/3DES 8 bytes). 그보다 긴 데이터를 어떻게 처리할지는 운영 모드가 정합니다. IV를 쓰지 않는 모드는 ECB뿐입니다.

3. 표준 IV 값이 있나요?

없습니다. 표준은 IV의 조건을 정할 뿐, 암호화에 쓸 고정 IV 값을 정하지 않습니다. NIST SP 800-38A Appendix C는 CBC IV가 예측 불가능(unpredictable)해야 한다고 요구합니다. 메시지마다 승인된 난수 생성기(random bit generator)로 만들거나, 고유한 nonce를 같은 키로 암호화해 만듭니다.

  • 이 페이지의 기본 IV 00 01 02 … 0f는 NIST SP 800-38A 테스트 벡터(test vector)의 값입니다. 결과를 재현하기 위해서만 사용합니다.
  • 고정 값은 다른 용도에만 있습니다. CBC-MAC과 CMAC은 0으로 채운 블록에서 시작하고, AES Key Wrap(RFC 3394)은 A6A6A6A6A6A6A6A6을 씁니다. 일반 암호화용 IV가 아닙니다.
  • 레거시 시스템에서 0으로 채운 IV나 0123456789abcdef 같은 문자열을 쓰기도 합니다. 이는 표준이 아니라 내부 약속일 뿐입니다. 같은 평문은 항상 같은 암호문이 되고, 예측 가능한 CBC IV는 선택 평문 공격(chosen-plaintext attack)을 가능하게 합니다(예: TLS 1.0의 BEAST).
4. "IV를 설정한 적이 없는데요?": 라이브러리 기본 동작

기본 IV 값이라는 것은 없습니다. 코드에서 IV를 지정하지 않으면 라이브러리는 무작위 IV를 만들거나, 비밀번호에서 IV를 유도(derive)하거나, IV가 없는 모드를 사용합니다.

5. "C#에서 IV 없이 암호화했는데 Java에서 풀렸어요." 왜 될까요?

무작위 IV를 쓰고 그 IV를 보내지 않았다면 Java는 첫 블록을 풀 수 없습니다. 그런데도 풀린다면 보통 다음 중 하나입니다.

  • 양쪽 모두 ECB 사용: C#의 aes.Mode = CipherMode.ECB 또는 aes.EncryptEcb(...), Java의 Cipher.getInstance("AES").
  • 비밀번호에서 IV 유도: Rfc2898DeriveBytes로 aes.Key와 aes.IV를 함께 만듦.
  • 공통 유틸리티(helper)가 IV를 설정: 흔히 키의 앞 16 bytes나 0으로 채운 배열. 즉 고정 IV.
  • IV를 암호문 앞에 붙여 전송: Java가 앞 16 bytes를 IV로 읽음. 이것이 올바른 방법.

간단한 확인 방법: 같은 키로 같은 평문을 두 번 암호화해 보세요. 결과가 같으면 ECB나 고정 IV이고, 다르면 무작위 IV가 데이터와 함께 전달되는 것입니다.

C#의 PaddingMode.PKCS7과 Java의 PKCS5Padding은 8/16-byte 블록에서 같은 방식입니다.

6. Padding과 "No padding"

ECB와 CBC는 블록 단위로만 동작하므로 마지막 블록을 padding으로 채웁니다.

Padding3 bytes 필요할 때비고
PKCS#703 03 03.NET, OpenSSL, Node.js, Java(PKCS5Padding)의 기본값. 길이가 이미 맞으면 1블록 전체를 추가.
ANSI X.92300 00 03항상 추가.
ISO/IEC 7816-480 00 00항상 추가.
Zero00 00 00필요할 때만 추가. 원래 데이터 끝의 0x00이 함께 사라짐.
None-호출하는 쪽이 블록 길이를 맞춰야 함.

"No padding"은 자동으로 채워 주지 않습니다. 라이브러리는 블록이 덜 찬 입력을 거부합니다: .NET "The input data is not a complete block.", Java IllegalBlockSizeException, OpenSSL "data not multiple of block length". CTR, GCM 같은 모드는 padding이 아예 필요 없습니다.
