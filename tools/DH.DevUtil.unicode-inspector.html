Characters, code points, and encodings

          
Unicode gives every character a number called a code point, written U+AC00. An encoding turns code points into bytes. UTF-8 uses 1–4 bytes per code point, UTF-16 uses one or two 16-bit code units, and CP949 uses 1 or 2 bytes but covers only Korean, a subset of Hanja, and common symbols.

Code points above U+FFFF need a surrogate pair in UTF-16, so "😀".length is 2 in JavaScript. Cutting a string by code units can split the pair and leave a broken lone surrogate. Use code points or grapheme segmentation (Intl.Segmenter) when you limit lengths for users.

          
Database column sizes

          
A Hangul syllable takes 3 bytes in UTF-8 and 2 bytes in CP949. A byte-sized column such as Oracle VARCHAR2(10 BYTE) in an AL32UTF8 database holds only 3 Hangul syllables. MySQL LENGTH() counts bytes, while CHAR_LENGTH() counts characters, and utf8mb4 is required for 4-byte characters such as emoji.

          
NFC and NFD

          
The same visible text can have different code points. NFC (composed) stores 한 as one code point, U+D55C. NFD (decomposed) stores it as three conjoining jamo, U+1112 U+1161 U+11AB. They look the same but compare as different strings, so search, deduplication, and file lookups fail. macOS has long used decomposed file names, so names copied from a Mac can appear as separated jamo such as ㅎㅏㄴㄱㅡㄹ on other systems. Normalize to NFC before comparing or storing text (str.normalize('NFC'), Java Normalizer, .NET string.Normalize(), Python unicodedata.normalize), and consider git config core.precomposeUnicode true on macOS.

          
NFKC/NFKD also fold compatibility characters: ｆｕｌｌ becomes full, ① becomes 1, and ㎏ becomes kg. That helps search and identifiers but loses formatting, so do not apply it to text you must preserve.

          
Hangul syllable composition

          
The 11,172 modern Hangul syllables U+AC00–U+D7A3 are computed, not listed: code = 0xAC00 + (initial × 21 + medial) × 28 + final, with 19 initial consonants, 21 vowels, and 28 finals (including "none"). The Description column uses this formula to split each syllable.

          
Hidden characters

          
Copy and paste from web pages, Word, chat apps, and PDFs often brings in characters you cannot see: U+00A0 no-break space, U+200B zero width space, U+FEFF BOM, and soft hyphens. They break string comparison, identifiers, CSV headers, and configuration keys. Bidirectional controls such as U+202E RLO can make source code display differently from what the compiler reads (the "Trojan Source" attack, CVE-2021-42574). Tag characters U+E0000–U+E007F are invisible and can hide text, for example instructions aimed at AI tools.

          
Byte order mark (BOM)

          
A BOM at the start of a file marks its encoding: EF BB BF for UTF-8, FF FE for UTF-16LE, FE FF for UTF-16BE. Excel needs the UTF-8 BOM to open a CSV as UTF-8, but a BOM breaks shell script shebang lines, and JSON (RFC 8259) must not start with one.

EUC-KR and CP949

          
EUC-KR is based on KS X 1001, which has only 2,350 Hangul syllables. Microsoft's CP949 (Unified Hangul Code) adds the remaining 8,822 so all 11,172 syllables fit. A syllable such as 똠 is CP949 8C 63 and has no EUC-KR code. Browsers implement the euc-kr label as CP949 (WHATWG Encoding Standard). Java calls it MS949, Python cp949, and .NET code page 949, which needs CodePagesEncodingProvider on .NET Core and later. CP949 cannot encode emoji or most other scripts; such characters become ? when saved.

        

        

          
문자, 코드 포인트(code point), 인코딩(encoding)

          
Unicode는 모든 문자에 코드 포인트라는 번호를 붙이고 U+AC00처럼 씁니다. 인코딩은 코드 포인트를 바이트로 바꾸는 규칙입니다. UTF-8은 코드 포인트 하나에 1~4바이트, UTF-16은 16-bit 코드 유닛(code unit) 1~2개를 쓰고, CP949는 1~2바이트를 쓰지만 한글, 일부 한자, 자주 쓰는 기호만 표현할 수 있습니다.

DB 컬럼 크기

          
한글 음절 하나는 UTF-8에서 3바이트, CP949에서 2바이트입니다. AL32UTF8 데이터베이스의 Oracle VARCHAR2(10 BYTE)처럼 바이트 단위 컬럼에는 한글이 3자만 들어갑니다. MySQL의 LENGTH()는 바이트를, CHAR_LENGTH()는 문자 수를 세며, 이모지 같은 4바이트 문자를 저장하려면 utf8mb4가 필요합니다.

          
NFC와 NFD

          
눈에 같은 텍스트도 코드 포인트는 다를 수 있습니다. NFC(조합형)는 한을 코드 포인트 하나(U+D55C)로, NFD(분해형)는 첫가끝 자모 세 개(U+1112 U+1161 U+11AB)로 저장합니다. 화면에서는 같아 보여도 다른 문자열이라 검색, 중복 제거, 파일 찾기가 실패합니다. macOS는 오래전부터 파일 이름을 분해형으로 다뤄 와서, Mac에서 복사한 파일 이름이 다른 시스템에서 ㅎㅏㄴㄱㅡㄹ처럼 자모가 분리되어 보일 수 있습니다. 비교하거나 저장하기 전에 NFC로 정규화하세요(str.normalize('NFC'), Java Normalizer, .NET string.Normalize(), Python unicodedata.normalize). macOS에서는 git config core.precomposeUnicode true도 고려하세요.

          
NFKC/NFKD는 호환 문자까지 바꿉니다. ｆｕｌｌ은 full, ①은 1, ㎏은 kg이 됩니다. 검색이나 식별자에는 도움이 되지만 서식이 사라지므로 원문을 보존해야 하는 텍스트에는 쓰지 마세요.

          
한글 음절 조합 공식

          
현대 한글 음절 11,172자(U+AC00–U+D7A3)는 목록이 아니라 계산으로 정해집니다. 코드 = 0xAC00 + (초성 × 21 + 중성) × 28 + 종성이며 초성 19개, 중성 21개, 종성 28개("없음" 포함)입니다. Description 열은 이 공식으로 음절을 분해해 보여 줍니다.

          
보이지 않는 문자

          
웹 페이지, Word, 메신저, PDF에서 복사하면 보이지 않는 문자가 자주 따라옵니다. U+00A0 줄바꿈 없는 공백(NBSP), U+200B 폭 없는 공백(ZWSP), U+FEFF BOM, 소프트 하이픈(soft hyphen) 등입니다. 이런 문자는 문자열 비교, 식별자, CSV 헤더, 설정 키를 깨뜨립니다. U+202E RLO 같은 양방향(bidi) 제어 문자는 소스 코드가 화면에 보이는 모습과 컴파일러가 읽는 내용을 다르게 만들 수 있습니다("Trojan Source" 공격, CVE-2021-42574). U+E0000–U+E007F 태그 문자(tag character)는 보이지 않아 AI 도구를 노린 지시문 같은 텍스트를 숨기는 데 쓰일 수 있습니다.

          
BOM(Byte Order Mark)

          
파일 맨 앞의 BOM은 인코딩을 표시합니다. UTF-8은 EF BB BF, UTF-16LE는 FF FE, UTF-16BE는 FE FF입니다. Excel이 CSV를 UTF-8로 열려면 UTF-8 BOM이 필요하지만, BOM은 셸 스크립트의 shebang 줄을 깨뜨리고, JSON(RFC 8259)은 BOM으로 시작하면 안 됩니다.

          
글자 깨짐(Mojibake)

EUC-KR과 CP949

          
EUC-KR은 한글 음절이 2,350자뿐인 KS X 1001을 기반으로 합니다. Microsoft의 CP949(통합형 한글 코드, Unified Hangul Code)는 나머지 8,822자를 더해 11,172자를 모두 표현합니다. 똠 같은 음절은 CP949로 8C 63이고 EUC-KR에는 코드가 없습니다. 브라우저는 euc-kr 레이블을 CP949로 구현합니다(WHATWG Encoding Standard). Java는 MS949, Python은 cp949, .NET은 코드 페이지 949라고 부르며 .NET Core 이후에는 CodePagesEncodingProvider가 필요합니다. CP949는 이모지와 대부분의 다른 문자를 표현하지 못해 저장하면 ?로 바뀝니다.
